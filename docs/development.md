# Development

## The one rule

**Never develop against a real Paperless-ngx library.**

PaperWrench modifies documents in bulk. A bug during development is not a
stack trace, it is three hundred renamed documents in somebody's archive. A
disposable Paperless-ngx 3.1.2 sandbox is one command away, and everything in
this project is built around using it.

## Requirements

- Python 3.11+
- Node.js 20+
- Docker and Docker Compose (for the sandbox and to build the image)
- `make`

## Setup

```bash
git clone https://github.com/flowent59/PaperWrench.git
cd PaperWrench
make install
```

This creates `backend/.venv`, installs the backend in editable mode with its
dev extras, and installs frontend dependencies from the lockfile.

## The development sandbox

```bash
make dev-paperless-up      # Paperless-ngx 3.1.2 on http://localhost:8010
make dev-paperless-seed    # reference dataset
```

Login is `admin` / `admin`. These credentials are intentionally trivial: the
stack binds to `127.0.0.1` and must never be exposed.

The version is pinned to **3.1.2** deliberately. That is the version whose
serialisers, filter lookups and API version negotiation were read and verified
during the architecture review (see [paperless-api.md](paperless-api.md)).
Bumping the tag means re-verifying those findings, not just changing a string.

### What the seed creates, and why

- Document type **`Relevé de vacations`** — the type used by the reference bulk
  rename scenario.
- Custom fields **`Période concernée`** (string) and **`Montant`** (monetary,
  EUR) — the fields that scenario reads.
- **Several additional custom fields**: `Référence interne`, `Établissement`,
  `Validé`, `Date de règlement`, `Commentaire`.

That last group is the important one. Paperless replaces a document's *entire*
custom field collection on a PATCH that includes `custom_fields`
([ADR-0004](decisions/0004-safe-custom-field-read-modify-write.md)). A naive
write of `Montant` deletes the other six fields, silently. Seeding several
fields per document means that bug fails a test instead of shipping.

Names and values are deliberately French — accents, spaces in field names, euro
amounts, `dd/mm/yyyy` dates — so encoding problems surface here rather than on a
real library.

Uploads are consumed asynchronously. After `make dev-paperless-seed`, wait for
the Paperless task queue to drain, then populate the field values:

```bash
docker compose -f docker-compose.dev.yml --profile seed run --rm seed \
  python seed_dev_custom_field_values.py
```

Both seed scripts refuse to run against anything whose hostname is not an exact
match for the sandbox. The check is on the parsed hostname, not a substring:
`paperless.my-real-domain.example` is rejected.

Tear it all down, data included:

```bash
make dev-paperless-down
```

## Running PaperWrench

Two terminals:

```bash
make dev-backend     # FastAPI with autoreload on :8000
make dev-frontend    # Vite dev server on :5173
```

Open <http://localhost:5173>. Vite proxies `/api` to the backend.

Point the backend at the sandbox with a `.env` in `backend/`:

```env
PAPERLESS_URL=http://localhost:8010
PAPERLESS_TOKEN=<token from the sandbox admin user>
PAPERWRENCH_DATABASE_URL=sqlite+pysqlite:///./data/paperwrench.db
PAPERWRENCH_LOG_FORMAT=console
PAPERWRENCH_CORS_ORIGINS=http://localhost:5173
```

`PAPERWRENCH_CORS_ORIGINS` is a development-only concession to the split-origin
setup. It is empty in production, where the SPA is served from the same origin
([ADR-0001](decisions/0001-single-container-vite-spa-fastapi.md)).

Note that development topology differs from production here, which is exactly
why the SPA fallback and the `/api` 404 behaviour are covered by tests rather
than assumed.

## Quality gates

```bash
make check      # everything CI runs
```

Individually:

```bash
make lint            # ruff + eslint
make typecheck       # mypy --strict + tsc -b
make test            # pytest + vitest
make format          # ruff autofix
make coverage        # backend coverage report
```

Both `mypy` strict mode and TypeScript strict mode are non-negotiable. In a
tool that mutates a live library, a type error is a data-loss bug that has not
happened yet.

`make check` must pass before opening a pull request; CI runs the same commands.

## Database

Migrations apply automatically at application startup, before the runtime lock
is acquired (the lock table is itself created by a migration). Manually:

```bash
make migrate                              # upgrade to head
make migration m="add transformation table"   # autogenerate
```

Always read an autogenerated migration before committing it. SQLite cannot
`ALTER` most things, so `render_as_batch=True` rewrites tables — check that the
rewrite preserves constraints, and in particular the uniqueness constraint on
`job_operations` that makes job resumption idempotent.

Revisions live inside the package at `backend/src/paperwrench/migrations/` so
the wheel is self-contained.

CI fails if the models and migrations have drifted: it autogenerates against an
up-to-date database and rejects the build if anything is emitted.

## Testing

```bash
cd backend && .venv/bin/pytest                     # unit + API
cd backend && .venv/bin/pytest -m live             # against the sandbox
cd backend && .venv/bin/pytest -m "not live"       # default
```

`live` tests require the sandbox to be running and seeded.

When adding a test for the write path, the useful question is not "does this
work" but "what does this stop from silently going wrong". The cases that must
always be covered:

- custom fields untouched by a single-field write, value by value;
- zero HTTP writes during a Dry Run;
- a document modified between preview and write yields `SKIPPED_CONFLICT`;
- a rollback refuses a document whose value moved after the write;
- a crash between the PATCH and the local commit, then a resume, produces
  exactly one write;
- concurrency never exceeds the configured bound;
- no log line contains the token.

Frontend tests use Vitest and jsdom:

```bash
cd frontend && npm run test
```

## Building

```bash
make build           # SPA into the package, then the wheel
make docker-build    # single-container image
```

The image is multi-stage: Node builds the SPA, Python builds a wheel that
embeds it, and the runtime stage installs only that wheel and runs as a
non-root user with a read-only root filesystem.

## Conventions

Code, identifiers, endpoints, commits and public documentation are in English.
Application *data* is whatever the user's library contains, which for the
reference dataset is French — accents, spaces in custom field names, euro
amounts. Both must work perfectly.

UI strings live in `frontend/src/i18n/messages.ts`. No component contains a
hardcoded user-facing string; a test enforces it. This is not a full i18n
framework and does not try to be — it is the minimum discipline that lets a
language be added later without restructuring the frontend.

Commits follow Conventional Commits (`feat:`, `fix:`, `docs:`, `refactor:`,
`test:`, `chore:`).

Branches: `feat/…`, `fix/…`, `docs/…`, `refactor/…`.

## Before touching the write path

Read [ADR-0003](decisions/0003-per-document-patch-as-mvp-write-path.md),
[ADR-0004](decisions/0004-safe-custom-field-read-modify-write.md) and
[ADR-0005](decisions/0005-written-value-and-optimistic-conflict-detection.md).
They are not background reading; they are the rules that code has to satisfy.
