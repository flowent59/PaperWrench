# Development

## The one rule

**Never develop against a real Paperless-ngx library.**

PaperWrench modifies documents in bulk. A bug during development is not a
stack trace, it is three hundred renamed documents in somebody's archive. A
disposable Paperless-ngx 3.1.2 sandbox is one command away, and everything in
this project is built around using it.

## Requirements

- Python 3.11+
- Node.js 20+
- Docker and Docker Compose (for the sandbox and to build the image)
- `make`

## Setup

```bash
git clone https://github.com/flowent59/PaperWrench.git
cd PaperWrench
make install
```

This creates `backend/.venv`, installs the backend in editable mode with its
dev extras, and installs frontend dependencies from the lockfile.

## The development sandbox

```bash
make dev-paperless-up      # Paperless-ngx 3.1.2 on http://localhost:8010
make dev-paperless-seed    # reference dataset
```

Login is `admin` / `admin`. These credentials are intentionally trivial: the
stack binds to `127.0.0.1` and must never be exposed.

The version is pinned to **3.1.2** deliberately. That is the version whose
serialisers, filter lookups and API version negotiation were read and verified
during the architecture review (see [paperless-api.md](paperless-api.md)).
Bumping the tag means re-verifying those findings, not just changing a string.

### What the seed creates, and why

- Document type **`Relevé de vacations`** — the type used by the reference bulk
  rename scenario.
- Custom fields **`Période concernée`** (string) and **`Montant`** (monetary,
  EUR) — the fields that scenario reads.
- **Several additional custom fields**: `Référence interne`, `Établissement`,
  `Validé`, `Date de règlement`, `Commentaire`.

That last group is the important one. Paperless replaces a document's *entire*
custom field collection on a PATCH that includes `custom_fields`
([ADR-0004](decisions/0004-safe-custom-field-read-modify-write.md)). A naive
write of `Montant` deletes the other six fields, silently. Seeding several
fields per document means that bug fails a test instead of shipping.

Names and values are deliberately French — accents, spaces in field names, euro
amounts, `dd/mm/yyyy` dates — so encoding problems surface here rather than on a
real library.

Uploads are consumed asynchronously. After `make dev-paperless-seed`, wait for
the Paperless task queue to drain, then populate the field values:

```bash
docker compose -f docker-compose.dev.yml --profile seed run --rm seed \
  python seed_dev_custom_field_values.py
```

Both seed scripts refuse to run against anything whose hostname is not an exact
match for the sandbox. The check is on the parsed hostname, not a substring:
`paperless.my-real-domain.example` is rejected.

Tear it all down, data included:

```bash
make dev-paperless-down
```

## Running PaperWrench

Two terminals:

```bash
make dev-backend     # FastAPI with autoreload on :8000
make dev-frontend    # Vite dev server on :5173
```

Open <http://localhost:5173>. Vite proxies `/api` to the backend.

Point the backend at the sandbox with a `.env` in `backend/`:

```env
PAPERLESS_URL=http://localhost:8010
PAPERLESS_TOKEN=<token from the sandbox admin user>
PAPERWRENCH_DATABASE_URL=sqlite+pysqlite:///./data/paperwrench.db
PAPERWRENCH_LOG_FORMAT=console
PAPERWRENCH_CORS_ORIGINS=http://localhost:5173
```

`PAPERWRENCH_CORS_ORIGINS` is a development-only concession to the split-origin
setup. It is empty in production, where the SPA is served from the same origin
([ADR-0001](decisions/0001-single-container-vite-spa-fastapi.md)).

Note that development topology differs from production here, which is exactly
why the SPA fallback and the `/api` 404 behaviour are covered by tests rather
than assumed.

## Quality gates

```bash
make check      # everything CI runs
```

Individually:

```bash
make lint            # ruff + eslint
make typecheck       # mypy --strict + tsc -b
make test            # pytest + vitest
make format          # ruff autofix
make coverage        # backend coverage report
```

Both `mypy` strict mode and TypeScript strict mode are non-negotiable. In a
tool that mutates a live library, a type error is a data-loss bug that has not
happened yet.

`make check` must pass before opening a pull request; CI runs the same commands.

## Database

Migrations apply automatically at application startup, before the runtime lock
is acquired (the lock table is itself created by a migration). Manually:

```bash
make migrate                              # upgrade to head
make migration m="add transformation table"   # autogenerate
```

Always read an autogenerated migration before committing it. SQLite cannot
`ALTER` most things, so `render_as_batch=True` rewrites tables — check that the
rewrite preserves constraints, and in particular the uniqueness constraint on
`job_operations` that preserves audit identity. Durable target states, not that
uniqueness constraint, prevent unsafe HTTP replay (ADR-0014).

Revisions live inside the package at `backend/src/paperwrench/migrations/` so
the wheel is self-contained.

CI fails if the models and migrations have drifted: it autogenerates against an
up-to-date database and rejects the build if anything is emitted.

## Testing

```bash
cd backend && .venv/bin/pytest                     # unit + API
cd backend && .venv/bin/pytest -m live             # against the sandbox
cd backend && .venv/bin/pytest -m "not live"       # default
```

`live` tests require the sandbox to be running and seeded.

When adding a test for the write path, the useful question is not "does this
work" but "what does this stop from silently going wrong". The cases that must
always be covered:

- custom fields untouched by a single-field write, value by value;
- zero HTTP writes during a Dry Run;
- a document modified between preview and write yields `SKIPPED_CONFLICT`;
- a rollback refuses a document whose value moved after the write;
- a crash between PATCH and local commit leaves ambiguous provenance and is
  never automatically replayed, even if current equals intended;
- concurrency never exceeds the configured bound;
- no log line contains the token.

### Working on the Filter Engine

`paperwrench/filters/` decides which documents a later transformation will
touch, and Paperless gives it no feedback when it gets that wrong — an
unknown filter parameter returns 200 and the whole library. Two rules follow.

**Every parameter the compiler can emit must be traceable to the 3.1.2
source.** Not to the OpenAPI schema, not to the upstream docs, and not to
what seems reasonable. `docs/paperless-api.md` §6.4–6.5 records the mappings
and where each was read; add to it when you add an operator.

**The engine stays pure.** `validate_filterset` and `compile_filterset` take
a `FieldCatalog` snapshot and perform no I/O. `filters/service.py` is the
only module that touches the Metadata Registry. Keep it that way: it is what
makes the compiler exhaustively testable, and it is what makes "a refused
filter costs zero requests to Paperless" true by construction rather than by
convention. `test_filter_no_fallback.py` asserts the absence of any
document-fetching call in the package, so adding one fails the suite.

Adding an operator means all of:

1. reading its behaviour in the Paperless source and recording it in
   `docs/paperless-api.md`;
2. adding it to the catalogue's operator matrix (`filters/catalog.py`) — for
   the *field*, not just the type, if it is a core field;
3. a compiler test asserting the exact parameters or expression it produces;
4. a validation test for each way its value can be wrong;
5. a live test if the semantics are anything other than obvious — and they
   usually are not: `is_null` requiring the field instance to exist, tags
   `all`/`any`/`none` being three different questions, and monetary
   comparison ignoring the currency code were all surprises.

If the operator cannot be compiled exactly, it does not go in. A filter that
is approximately right is the one failure mode this whole subsystem exists
to prevent.

Frontend tests use Vitest and jsdom:

```bash
cd frontend && npm run test
```

## Building

```bash
make build           # SPA into the package, then the wheel
make docker-build    # single-container image
```

The image is multi-stage: Node builds the SPA, Python builds a wheel that
embeds it, and the runtime stage installs only that wheel and runs as a
non-root user with a read-only root filesystem.

## Conventions

Code, identifiers, endpoints, commits and public documentation are in English.
Application *data* is whatever the user's library contains, which for the
reference dataset is French — accents, spaces in custom field names, euro
amounts. Both must work perfectly.

UI strings live in `frontend/src/i18n/messages.ts`. No component contains a
hardcoded user-facing string; a test enforces it. This is not a full i18n
framework and does not try to be — it is the minimum discipline that lets a
language be added later without restructuring the frontend.

Commits follow Conventional Commits (`feat:`, `fix:`, `docs:`, `refactor:`,
`test:`, `chore:`).

Branches: `feat/…`, `fix/…`, `docs/…`, `refactor/…`.

## Before touching the write path

Read [ADR-0003](decisions/0003-per-document-patch-as-mvp-write-path.md),
[ADR-0004](decisions/0004-safe-custom-field-read-modify-write.md) and
[ADR-0005](decisions/0005-written-value-and-optimistic-conflict-detection.md).
They are not background reading; they are the rules that code has to satisfy.

## Working on M6 transformations

The M6 domain API is `validate(Transformation, definitions_by_id)` and
`evaluate(Document, Transformation, definitions_by_id)`.
Build the `definitions_by_id` snapshot from `MetadataRegistry.all_custom_fields()`
outside both functions. They neither fetch nor write. The API's
single-document route performs GETs only; it is an authoring check, not the M7
dataset-wide Dry Run.

Specifications have a target source (`ids` or the existing `DatasetQuery`) and
one or more unique target fields. Custom fields use `CustomFieldRef.field_id`.
For a title template such as `Relevé de vacations – {Période concernée}`,
bind the placeholder explicitly to a custom `FieldRef` by ID. Placeholder
names are local aliases, never lookup keys. Missing, null and empty values
produce `TEMPLATE_UNRESOLVED`; unknown definitions and unsupported types have
their own errors. Monetary SET values are exact strings such as `EUR0.00`,
Select SET values are option IDs, and custom CLEAR must explicitly choose
`absent` or `null`. The renderer uses a Select label for display, but that
label is never an identity or write value.

Run `pytest tests/backend/unit/test_transformations.py` for the pure matrix and
the guarded zero-write API check. Frontend authoring serialization is covered
by `frontend/src/pages/transformations/model.test.ts`. M7/M8 must recheck the
document and metadata at their own boundary; an M6 proposal is based only on
the supplied state.

## Working on M7 previews

Read [ADR-0013](decisions/0013-expiring-preview-staging-and-confirmation.md) and
the [preview API contract](preview-api.md). Reuse M6 `evaluate()`; do not add
another SET/CLEAR/REPLACE/TEMPLATE implementation. Preview GETs use the lifecycle
PaperlessClient. There is no document mutation call in the preview service.

`iter_documents()` is now an async generator. Use `async for document in
client.iter_documents(...)`; collect explicitly only in small controlled tests.
M7 uses `list_documents()` to retain each page's count/next envelope, commits
one batch before the next GET and never keeps a library-sized Document array.

The two staging tables are migrated by Alembic, separate from dormant Job
tables. TTL is 30 minutes; interrupted builds are removed at startup. Explicit
limits are 100,000 documents, 128 MiB result JSON, five-minute build deadline,
one active builder and four retained previews. API/UI pages remain bounded.
No partial preview is returned on a limit/fatal error. Local deletion is not
secure erasure; the SQLite file can retain/reuse allocated pages.

Focused checks:

```sh
pytest tests/backend/unit/test_previews.py tests/backend/integration_mocked/test_preview_bounds.py
PAPERWRENCH_ALLOW_LIVE_TESTS=true PAPERWRENCH_LIVE_PAPERLESS_URL=http://127.0.0.1:8010 pytest tests/backend/live/test_previews_live.py -v
cd frontend && npm test -- --run src/pages/transformations
```

The live probe uses only GETs after the guarded Golden Dataset setup. It checks
compiled document-type selection, counts, small traversal pages, the vacation
title template, missing periods, EUR0.00 and identical normalized documents
after preview. Synthetic 10k tests verify bounded Document retention and staged
batches, not live 10k performance. 50k/100k live capacity remains NOT_RUN.

Preview's original confirmation route remains local review only. M8 Apply uses
`PreviewService.claim(session, ...)` inside the Job creation transaction, copies
exact staged targets, then rechecks documents and metadata before writing.
Do not turn the review endpoint into implicit Apply. Never add `written_value`
to M7 preview results.

## Working on M8 Jobs

Read [ADR-0014](decisions/0014-durable-jobs-and-write-provenance.md) and the
[Job API](job-api.md). The fixed worker pool uses the lifecycle PaperlessClient
and M5 coordinator. Its semaphore bounds mutations across Jobs and Inspector.

Creation copies target rows in bounded batches within one transaction. Execution
holds no database transaction during HTTP. Before send, commit fresh before
values and the writing marker. After acknowledged PATCH, GET actual values.
Never assign intended to written or infer provenance after restart. An old
runtime must not overwrite evidence already recovered by a new runtime.

On startup unsent work requires explicit resume. `PAPERWRENCH_AUTO_RESUME_JOBS`
remains false; true is rejected. Lock loss is latched until restart. Shutdown
cancels workers and records uncertainty according to the send marker. Forced
takeover cannot retract an HTTP request already sent to Paperless.

Focused checks:

```sh
pytest tests/backend/unit/test_jobs.py tests/backend/unit/test_api_jobs.py tests/backend/unit/test_job_migrations.py
pytest tests/backend/integration_mocked/test_preview_bounds.py -s
PAPERWRENCH_ALLOW_LIVE_TESTS=true PAPERWRENCH_LIVE_PAPERLESS_URL=http://127.0.0.1:8010 pytest tests/backend/live/test_jobs_live.py -v
cd frontend && npm test -- --run src/pages/jobs src/pages/transformations/dry-run.test.tsx
```

Guarded live tests restore Golden Dataset titles and remove scratch data. They
check the vacation template, normalization, custom neighbours, lost permissions,
hidden documents, and a real PATCH followed by injected response loss.
`job_crash_child.py` exits a real subprocess before intent, before PATCH, after
PATCH, after readback and after durable result commit. Its credential is passed
through the environment, never command arguments/output. This verifies process
crash handling, not power-loss durability or a real proxy outage.

## Working on M5 writes

Read ADR-0012 as well as ADR-0002–0005/0009. Use the lifecycle PaperlessClient:
`update_document` accepts only core allowlisted keys; `mutate_document` combines
core/custom operations with a required document revision. Never pass a custom
replacement array. All writers for this instance must share its coordinator.
The compatibility custom helper now requires `acknowledge_external_race=True`;
this is deliberate API tightening, including for sandbox callers.

Inspector's `PATCH /api/v1/documents/{id}` accepts `expected_revision`,
`catalog_revision`, `core`, `custom_changes` and `acknowledge_external_race` only.
A custom change is `{field_id, kind, value}`; omit value for absent/null. Empty
string is a present text value; monetary values are currency-prefixed exact
strings; selects take opaque option IDs. Unknown keys, duplicate operations and
unsupported types fail before PATCH. Core references are IDs, not names.

Run focused tests, then all existing CI gates:

```sh
pytest tests/backend/unit/test_inspector.py tests/backend/integration_mocked
PAPERWRENCH_ALLOW_LIVE_TESTS=true PAPERWRENCH_LIVE_PAPERLESS_URL=http://127.0.0.1:8010 pytest tests/backend/live -v
cd frontend && npm test
```

The existing guarded sandbox fixture supplies a disposable credential; never use
personal credentials. M5 live tests use disposable scratch documents and remove
created select definitions/users. `test_inspector_live.py` checks the acceptance
scenario, deterministic internal/external interleaving and ineffective conditional
headers. The external-race test deliberately demonstrates loss on scratch data;
it must never be repurposed for a real library. Operator quiescence is ASSUMED.

`make check` does not replace the guarded live, migration and Docker CI jobs.
CI's complete gate list in `.github/workflows/ci.yml` remains mandatory.
On Windows, the runtime instance ID uses portable `platform.node()`; Linux
Python 3.11 CI remains authoritative for the production environment.
