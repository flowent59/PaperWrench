# Translating PaperWrench

PaperWrench ships complete English (`en`) and French (`fr`) interfaces. Translation files are JSON, grouped by product domain under `frontend/src/i18n/locales/<locale>/`; for example, job-history strings live in `jobs.json` and authentication strings in `auth.json`. English is the reference catalogue.

## Changing user-facing text

Every UI change must update all supported locales in the same pull request. Add the same domain file, nested key and value shape to `en` and `fr`; components continue to read the typed `messages.<domain>.<key>` API from `frontend/src/i18n/messages.ts`. Do not put translated text directly in JSX, and do not translate Paperless-owned data such as custom-field names or select-option labels.

Dynamic values use named placeholders such as `{count}`, `{name}` or `{status}`. A translation must contain exactly the placeholders used by English. Plural messages use this shape:

```json
{
  "_type": "plural",
  "one": "{count} document",
  "other": "{count} documents"
}
```

Both `one` and `other` are required for EN/FR. Lookup descriptors translate stable application identifiers while retaining a fallback for unknown values; keep their keys aligned across locales.

Run the translation gate before opening a pull request:

```bash
cd frontend
npm run i18n:check
npm run test:i18n-validator
npm run test
```

CI rejects malformed JSON, missing or extra nested keys, mismatched placeholders, and missing or invalid plural forms. Representative Playwright coverage also exercises EN/FR rendering, locale persistence, and locale-aware number/date formatting.

## Adding a locale

1. Copy `frontend/src/i18n/locales/en/` to a new normalized locale directory and translate every value without changing keys or placeholders.
2. Add the locale imports and catalogue entry in `frontend/src/i18n/catalogs.ts`.
3. Add the locale to the frontend selector and backend preference validation/database migration.
4. Map the locale to its BCP 47 formatting tag in `frontend/src/i18n/format.ts`.
5. Extend `REQUIRED_LOCALES` in `frontend/scripts/validate-i18n.mjs` and add Playwright coverage for detection, persistence, and `Intl` output.
6. Update the locale decision record and user documentation, then run the complete `make check` suite.

Community translation pull requests should stay focused on one locale or domain, explain who reviewed the language, and avoid unrelated code changes. Screenshots help reviewers with context but never replace the automated completeness gate.
